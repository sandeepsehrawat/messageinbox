    Developer Notes¶

    All DTO schemas are defined inside the OpenAPI under components.schemas.
    Treat those as the canonical data contracts for the Message Inbox LLD.

    Caching¶

    • Mobile:
    • Use local cache (e.g. SQLite / secure storage) for messages[] and totalUnread.
    • Refresh cache on:
      • app resume,
      • explicit pull-to-refresh,
      • successful mark-as-read.
    • Web:
      • Use session storage (or in-memory cache) for the current page of messages.
      • Always re-fetch on full page reload or login.
    • Rules:
    • Cache is an optimization only – server state (Process/System APIs) is source of truth.
    • After any mutating operation (mark read), either:
      • update cache locally, and/or
      • re-fetch /messages/unread to reconcile.

    Push Notifications¶

    • Triggering:
    • Process layer (or upstream command services) should only trigger push when:
      • status = "unread",
      • pushNotification = true,
      • user preferences allow notifications.
    • Behaviour after read:
    • Once message is marked read:
      • no further notifications for that message,
      • decremented badge count on device (if supported by push provider).
    • Delivery:
      • Use existing notification infrastructure (e.g. Firebase/APNs) via a NotificationDispatchService.
      • Device token management and invalid token cleanup handled centrally, not in inbox code.

    Edge Cases¶

    • Offline mode (mobile):
      • Allow reading from cached messages.
      • Queue mark-read requests locally and replay when online.
      • After sync, re-fetch unread messages to reconcile unreadCount.
    • Partial message fetch:
      • If one downstream system fails (e.g. BulkMessageSystemAPI), still return what is available.
      • Use flags such as partialResult and/or degradedMode to inform UI.
    • Multi-device sync:
      • Read state is persisted in MessageSystemAPI.
      • Any device calling /messages/unread sees the same latest status and unreadCount.
    • Duplicate prevention:
      • Deduplicate by messageId when merging system + bulk sources.

    Testing Recommendations¶

    • Functional:
      • Validate unread count after each mark-message-read call.
      • Verify that bulk + system messages are merged and sorted correctly.
      • Test filters (by status, category, date range) and pagination boundaries.
    • Negative & security:
      • Requests with invalid/missing Authorization → 401.
      • Requests where userId in payload does not match JWT → 403.
      • Accessing a message not owned by user → 403 / 404 (as per design).
    • Resilience:
      • Simulate downstream failures:
        • Bulk API down,
        • User preferences API delayed.
      • Confirm partialResult behaviour and logging.
    • Offline & sync:
      • Simulate offline mark-read queueing and later reconciliation.
      • Ensure unread badges align after reconnect + refresh.

    Security¶

    • Authentication & Authorization:
      • Use JWT bearer tokens at Channel API level.
      • Process API should receive an already-authenticated principal (service-to-service auth).
      • Always validate that userId in payload matches the subject in the token (ownership).
    • Data protection:
      • Treat message content as potentially sensitive (account / corporate info).
      • Avoid logging full content; log IDs and correlation IDs instead.
    • Audit:
      • Audit log for:
        • message read events,
        • bulk message creation,
        • security violations (ownership failures).

    Performance¶

    • Pagination:
      • Enforce page size limits (default 20, max 50) to prevent huge payloads.
      • Keep sorting stable (timestampUtc desc) to avoid issues with paging.
    • Aggregation & orchestration:
      • Prefer a single call from Channel → Process for unread messages.
      • Inside Process API:
        • fan-out to System APIs in parallel where possible,
        • aggregate results, dedupe, map DTOs.

    Assumptions¶

    • Mobile/web apps:
      • cache unread IDs / message summaries locally for performance,
      • always reconcile with backend periodically.
    • System APIs:
      • expose stable identifiers and timestamps,
      • are generally available and within agreed SLAs.
    • Notification infrastructure:
      • already exists (e.g. Firebase/APNs push layer),
      • handles device token management and low-level delivery concerns.
    • Bulk messages:
      • are precomputed and stored in Bulk/Message systems,
      • are filtered per user by the Process layer before returning to clients.

    Additional Developer Considerations¶

    • DTO versioning:
      • If MessageSummaryDTO / MessageDetailDTO evolve, add fields in a backward-compatible way.
      • For breaking changes, consider versioned endpoints or versioned DTOs.
    • Idempotency:
      • mark-message-read must be idempotent:
        • repeated calls for the same messageId must not double-decrement unreadCount.
    • Observability:
      • Implement structured logging with correlation IDs per request.
      • Expose metrics:
        • latency per endpoint,
        • count of degraded responses,
        • error-rate per downstream dependency.
    • Configuration:
      • Page sizes, notification thresholds, and retention windows should be configurable (not hard-coded).

    These Developer Notes, together with the OpenAPI spec, Functional Notes, Assumptions, and Sequence Diagrams, are intended to give engineers everything they need to implement and operate the Message Inbox APIs confidently.
