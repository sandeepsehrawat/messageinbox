Assumptions for Message Inbox API Design (LLD)¶

Architecture Assumptions¶

NOTE – This Low-Level Design (LLD) primarily defines the Process API for the Message Inbox solution.

  • Channel API considerations are included to outline how the UI will consume the messages (pagination, caching, unread counts, push handling).
  • System API considerations are treated as upstream dependencies assumed to already exist (raw data, bulk store, user preferences, message metadata).
  • The focus of this LLD is on orchestration, validation, transformation, unread computation, and integration logic inside the Process API, because that is where the actual business rules, aggregation, and message preparation for the client occur.

SPC Architecture¶

  • The API design follows a System → Process → Channel (SPC) architecture.
  • System APIs provide raw data.
  • Process APIs orchestrate, validate, transform, and compute unread counts.
  • Channel APIs expose endpoints to web and mobile clients.

Pull-Based Model¶

  • The solution is primarily pull-based; users fetch messages when they log in or refresh their inbox.
  • System messages are user-specific and available immediately on login.
  • Bulk messages exist in a centralized bulk message store; they are aggregated and filtered per user at fetch time.

Push Notifications (Optional / Complementary)¶

  • High-priority messages may trigger push notifications or in-app alerts.
  • Push notifications only signal the user; full message content is retrieved via the pull API.

Central Bulk Message System¶

  • A centralized system manages the creation and storage of bulk messages for multiple users.
  • Users do not store bulk messages locally until they fetch them from the Process API.

Multi-Device Support¶

  • Users may access the inbox via multiple devices (mobile and web).
  • Read/unread status must be synchronized across devices.

Offline Caching¶

  • Mobile clients cache unread message IDs and content for offline viewing.
  • Web clients may cache in session storage.
  • Offline updates (e.g., marking a message read) are synced once online.

Error Handling¶

  • Partial failures in System APIs or Bulk APIs do not break the entire inbox fetch.
  • Error codes include standard HTTP responses: 401, 404, 500.

Functional Assumptions¶

Message Types¶

  • System Messages: Critical updates, account changes, corporate actions.
  • Bulk Messages: Aggregated notifications, such as dividends or portfolio updates.

Validation & Transformation¶

  • All messages must have mandatory fields: messageId, title, content, timestamp.
  • Bulk messages are aggregated and filtered per user.
  • Timestamps may be localized based on user preferences.

Unread / Read Tracking¶

  • Unread counts are maintained on the client and in the Process API.
  • Read status updates propagate to all devices for consistency.

Scalability¶

  • Users may have hundreds or thousands of messages.
  • Pagination and filtering are applied to reduce payloads.

Security¶

  • APIs are secured with JWT authentication.
  • User ID is validated from the token for all API calls.

Push Notifications¶

  • Only messages flagged pushNotification: true trigger notifications.
  • Notification respects user preferences (opt-in/out).

Aggregation¶

  • Bulk messages are aggregated per user at fetch time.
  • Aggregation ensures that each user sees only relevant messages.

Operational Assumptions¶

  • System APIs and Bulk APIs are assumed to be available and responsive most of the time.
  • Messages remain in the inbox until marked read or archived.
  • Push notifications may be delayed in case of device offline or network issues.
  • The design allows new message types or additional backend systems to be integrated without major changes.
